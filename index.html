TL;DR: LatentShield makes latent multi-agent collaboration monitorable: agents communicate in latent space within each MDU, while safety checks precede the token-space decisions passed between MDUs.

Abstract

From TextMAS to LatentMAS

In a text multi-agent system (TextMAS), several language-model agents work on a task together by exchanging written messages. A text-based safety monitor can read these messages to check for unsafe behavior. Generating each message takes time and can leave out information held in the agent's internal state.

A latent multi-agent system (LatentMAS) lets agents collaborate by exchanging their internal numerical representations, called latent states. Passing these states directly preserves information that text generation can discard and avoids repeatedly generating and re-encoding intermediate messages. In its reported experiments, LatentMAS improves reasoning accuracy while using fewer output tokens and running faster than its text-based multi-agent baselines.

The intermediate text trace disappears in LatentMAS. Conventional text-based monitors lose access to the collaboration that produces the final answer. We aim to design a scalable monitoring framework for LatentMAS.

Overview

LatentShield uses local LatentMAS teams as reusable building blocks, called Multi-Agent Decision Units (MDUs), to construct larger workflows. Within each MDU, contributor agents collaborate through latent states, retaining information that text generation can discard. Before the unit's designated decision node generates an output, LatentShield checks the contributors' latent trajectory and adds a safety instruction if the predicted risk exceeds a threshold. The decision node then passes a token-space message to downstream MDUs. This gives every unit a defined point for monitoring and lets us scale the workflow without propagating its full latent history across units, while preserving latent collaboration within each team.

Learning to monitor latent collaboration

At an MDU's decision boundary, the monitor can access the states produced by all contributor agents. We collect these states into a latent trajectory and train LatentShield to estimate whether the decision node's next output will comply with a harmful request. Trajectories vary in length, and the agents' representations differ from those used by Llama Guard, the safety model we use to assess risk. A learned readout pools each trajectory and maps it into Llama Guard's representation space. Training adjusts this readout while keeping the weights of the agents and Llama Guard fixed.

From a variable-length trajectory to one score

A learned query assigns a weight to each contributor state and combines the states into one fixed-size vector. During training, the query learns to give more weight to states that help predict harmful compliance. A small two-layer neural network, the MLP aligner, maps the pooled vector into the internal representation space of Llama-Guard-3-8B. We insert this vector at an intermediate layer. The remaining frozen layers produce scores for the safe and unsafe labels, which we normalize to obtain a risk score.

Learn from completed outputs

  1. Run training requests through the MDU. Save the contributor trajectory at the boundary and the decision node's subsequent output.
  2. Label harmful compliance using the dataset's prompt annotations and WildGuard's response annotations. A harmful request that receives a refusal is labeled negative.
  3. Train the attention query and MLP with weighted binary cross-entropy. Gradients pass through Llama Guard, but its weights and the agent backbone stay fixed.

At runtime, the monitor reads the contributor trajectory before the decision node generates.

Use the score before generation

We choose an intervention threshold using held-out validation trajectories, then keep it fixed during testing. At each decision boundary, the monitor compares its risk score with this threshold. A score above the threshold triggers a safety instruction in the decision node's prompt before generation begins. The contributor computation and the decision node's accumulated latent context are preserved, so the intervention changes how the node is instructed to respond.

Above the threshold

Add an instruction asking the decision node to refuse briefly and avoid continuing the flagged reasoning. The decision node then generates the output.

At or below the threshold

The decision node generates from its normal input. No safety instruction is added.

The \(p_{10}\) operating point sets the threshold at a \(10\%\) false-positive rate on benign validation trajectories. This threshold stays fixed during testing.

Safety and utility across five backbones

We evaluate whether monitoring reduces harmful compliance while preserving useful responses to benign requests. Each experiment uses one of five language models as the backbone shared by all agents, with a separate monitor trained for each backbone. We compare LatentShield with unguarded LatentMAS, a guard that inspects decoded text (CoT Guard), a guard that asks the backbone to judge its latent computation (Backbone Guard), and a learned linear classifier (Linear Probe). Mean failure rate (MFR) averages four benchmark rates: two measure compliance with harmful requests, and two measure unnecessary refusal of benign requests. Each benchmark has equal weight, and lower MFR is better. On Qwen3-4B at \(p_{10}\), MFR falls from \(0.174\) to \(0.111\), a \(36.2\%\) reduction relative to unguarded LatentMAS.

Preserving useful reasoning

We also test whether monitored teams can still solve benign reasoning problems. GPQA-Diamond and MMLU-Pro measure answer accuracy, complementing the refusal-based benchmarks above. We evaluate the same five backbones and compare monitored LatentMAS with the unguarded system and text-based multi-agent references. LatentShield retains competitive accuracy overall across these tasks, with performance varying by backbone and operating point.

Generalization to unseen MDU structures

Changing the number of agents or the way they communicate changes the latent trajectory presented to the monitor. We test whether a monitor learned on one team can still assess these new trajectories. Using Qwen3-4B throughout, we train on a four-agent chain and apply the frozen monitor to six unseen structures with five, six, or nine agents. Its \(p_{10}\) threshold is calibrated on the source chain and stays fixed for every target structure. LatentShield reduces MFR relative to unguarded LatentMAS on all six evaluated structures.

Composing MDUs into larger workflows

MDUs can be connected in chains, branches, or merging paths, so a workflow can combine teams with different internal structures. Only token-space messages cross MDU boundaries. Each receiving unit processes those messages through its own latent collaboration, and LatentShield checks its completed contributor trajectory before the next output is generated. This check also assesses the combined context when messages arrive from several branches. In our composed Qwen3-4B experiment, a monitor runs at every MDU boundary, and we evaluate the final workflow response on the same four safety benchmarks. At \(p_{01}\), LatentShield lowers MFR from \(0.099\) for the unguarded workflow to \(0.090\).

Additional evaluations

We also evaluate monitoring under adaptive prompt injection and in tasks that produce actions. PIArena generates adaptive attacks against the Qwen3-14B system, testing the monitor under adversarial prompts beyond the standard benchmark setting. In DTap, an MDU can produce an action such as a tool call, and LatentShield checks the trajectory before that action is generated. We measure both direct attack success and successful completion of benign tasks. LatentShield reduces direct attack success while increasing benign completion in this evaluation.
